# Security boundaries

## Offline event reading — source verified, bounded GM native acceptance passed

Offline reading is an opt-in world setting, off by default. Task29 stores `{enabled:false, retentionDays:14}` and bounds retention to integer days from 1 to 365. PR #76 is merged. Source `e28f836ae8a83116d59f0f75174d684c9917c5a7` passed build/lint and 3,427 fast / 2,227 slow tests. Bounded GM native acceptance passed on Foundry 13.351/14.369; this does not broaden the software trust boundary.

Player gateways enforce this setting **by software, not cryptography**. The gateway trusts policy observations from its authenticated paired module; it does not independently attest that the sender is a native GM or that the world setting is still current. The legitimate module reads the world setting and restricts editing/purge controls to a freshly checked native GM. A modified gateway or paired client can evade these cooperative checks. An unreachable gateway cannot discover a later world-policy change; it uses the last accepted setting until an authenticated update arrives. This does not solve Task18's immediate cross-owner/offline invalidation blocker.

Offline reads require both a persisted enabled world policy and the exact active pairing's last accepted explicit read allow. Missing state, ask/deny/disabled authorization and revoked pairings fail closed. A fresh connection must clear or withhold prior read permission until that connection accepts valid affirmative metadata; a connection that drops before announcing cannot resurrect old offline permission. Sessions started with `--user` remain fixed to one world/user/agent identity. Without `--user` (follow mode, task 71) a session binds to the one connected pairing and may re-bind to another only when the bound pairing is offline and the other is the only connected one; a re-bind clears the event and queue owner pins, and the module still records the user its own server set for the connection. First offline selection uses an unambiguous persisted exact ID, never a user-name fallback, and replacement pairings inherit neither prior authorization nor rows.

Retention uses gateway receipt time rather than event-supplied timestamps, running at startup and hourly. Purge and retention remove payloads transactionally while preserving monotonic cursor high-water and truthful deletion gaps. The purge target is the authenticated connection's world at that receiving gateway, not caller-supplied world/user IDs or every gateway in the network. The module's legitimate purge action requires fresh GM checks; the gateway's paired-module trust must not be presented as independent GM attestation. A correlated reply reports the deletion count without deleting credentials, policy or cursor high-water.

Both peers must upgrade together to protocol **5.0.0** for Task29's strict policy/purge frames. Earlier protocol4 native proof establishes only Task28's bounded online behavior. Task29 native acceptance at `88b27ca` / bundle `d19791ab` used actual GM policy saves, enabled/disabled offline reads and isolated-buffer purge/count checks, with original world setting and baselines restored. It does not establish native player/offline revocation, retention timing or installed deployment. Combined verification passed (build/lint, 3,437 fast / 2,227 slow); reusable-harness validation is merged in PR #78. Future native mutations still require scoped consent, isolated test-buffer storage and guarded restoration of any changed world setting.

## Local HTTP transport — task 34

`--http` serves MCP on `127.0.0.1` only; any other bind address is refused unless a public URL is set (see "Public mode" below, where the static bearer is off). Every request needs a bearer token, which is generated on first run, printed once, and stored only as a hash in the SQLite store (`gateway_settings`). Comparison is constant-time and the hash is read on every request, so `--http-rotate-token` takes effect without a restart. Rotation never migrates the database. Requests are bounded by a body size limit (413), a per-token rate limit (429), a session cap (503) and idle session close. `/status` is loopback-only and shows no secrets, with world and user names HTML-escaped. Only the primary serves HTTP. This adds a local network surface: any local process holding the token can use the gateway as the paired user.

## The permission model in this release — task 65

This section describes what the gateway enforces. Layers apply strictest-first, and a call must pass every one.

1. **OAuth token scopes (remote clients only).** A client that connects through a public URL holds a token with some of `read`, `write`, `destructive` and `code`. The gateway filters the tool list by those scopes and refuses a call outside them before it reaches the module, the offline queue or the event reader. A local stdio or `--http` session has no scopes and starts at layer 2. Scopes only narrow what the layers below allow; no scope grants anything the role, policy or approvals would refuse. See "Remote access and OAuth".
2. **Role tool set.** The tools an agent sees come from the bound Foundry user's role, as Foundry reports it over the authenticated link. No gateway setting and no MCP input chooses the role. A GM-only tool is refused for a non-GM at call time as well as hidden from the list.
3. **World policy.** The GM sets, per role and tool category (read, write, destructive, code), whether a call is allowed, asked of the owner, asked of a GM or denied. Agents for non-GM users are off until a GM enables them. Code execution cannot be set to run without asking.
4. **Rate limits.** Per-category limits are enforced in the module, so a runaway agent is slowed whatever the client does.
5. **Approvals.** A call that needs approval waits for a human in Foundry and returns a pending status if nobody answers in time. A denial carries its reason back to the agent. Nothing changes in the world until the call is approved.
6. **Audit and Undo.** Every write is recorded in the GM-only Agent Gateway Audit journal. A GM can undo the targets a call declared, for these world document types: Actor, Item, JournalEntry, Scene, RollTable, Playlist, Cards, Folder and ChatMessage, plus the embedded documents of those that Undo can recreate (`module/src/audit/undo-classes.ts:6-35`). Undo does not cover User, Setting, Macro or Adventure, and it refuses a target whose snapshot was too large to keep. Approved `script_run` and `macro_run` calls run arbitrary JavaScript with Foundry's native access, and the audit snapshots only declared targets (`module/src/tools/script-run.ts` declares none), so code can change settings or documents that Undo cannot reverse. Approve code only if you would accept its change without Undo. Approving code also trusts it with the audit record itself. A GM's `script_run` is given the live `game` object (`module/src/tools/script-run.ts:14`), so it can delete the audit journal. The gateway module does not recreate the journal while its designation setting is set (`module/src/audit/journal.ts:94-96,124`), a later write then throws (`journal.ts:192-193`), and that failure is only caught and logged (`module/src/audit/relay.ts:105-106,236-237`). Approved code can therefore erase earlier records and leave its own action unrecorded.
7. **Foundry's own permission checks** apply to the user the agent acts as, on top of all of the above.

### Pairing, code confirmation and token storage

A browser pairs with the gateway only by entering a one-time pairing code. The gateway shows the code in its own stderr, in the connected client's MCP log, and through `gateway_status` or a not-connected error in chat. All of those are local to the owner, in local mode. With a public URL the code appears only in the operator's log and console; it is never in `gateway_status`, a not-connected error or an MCP log notice, because those reach the AI client, which may be a cloud service. Protect that log. A code is valid for 10 minutes and works once. After 10 wrong codes in 60 seconds, counted across all origins, make the gateway refuse further codes until the window passes. A wrong guess does not spend the real code. In server mode there is no shared code at all. The operator makes an invite with `--invite <world> <user>` instead. An invite works once, is bound to exactly one world and one user, and is valid for 24 hours unless `--ttl` says otherwise (7 days at most). The gateway stores only a hash and prints the invite once. A plain player invite also needs a live admin GM to confirm it, and the operator-only `--gm` and `--admin` invites skip that and are short-lived; see `--help`. Wrong or expired invites count in the same per-client and global failed-code limits as codes. The gateway also checks the `Host` header of the link connection against DNS rebinding.

A pairing is made from a specific browser origin and its token works only from that origin, so `http://` and `https://` addresses of one host pair separately. A page on any other origin cannot reuse a token it learned. Pairings made before origin binding were retired and need one re-pair.

The pairing token is stored in two places. The browser keeps it in that origin's localStorage as a client-side Foundry setting. The gateway keeps only a hash of it, in the `pairings` table of its SQLite store at `~/.foundry-agent-gateway/gateway.db`. A leaked database does not reveal tokens, but anyone who can read the browser's localStorage for that origin can use that browser's pairing.

### HTTP bearer token

The local HTTP option (above, "Local HTTP transport") binds to `127.0.0.1` only. Its bearer token is shown once on first run and only its hash is stored, in the same SQLite store. Whoever holds the token can use the gateway as the paired user, so keep it out of chat, logs and version control, and rotate it with `--http-rotate-token` if it leaks. With a public URL there is no bearer token: it is off, and a request that carries the old token gets 401. Remote clients authenticate only through OAuth (see "Remote access and OAuth").

### Relay between gateway instances

Claude Desktop can start several gateway processes from one extension. One holds the link port and the store. The others forward their MCP traffic to it over a private local channel: a Unix domain socket in the state directory on macOS and Linux, and a named pipe on Windows. The channel is protected twice. The state directory and socket are readable by your user only, and the primary writes a per-boot random secret, mode 0600, in the state directory, which a relaying instance must present first. On Windows the pipe name also carries a random per-boot suffix published only in that secret file. The relay carries MCP messages only; identity is never read from them. Each relayed connection gets its own full session on the primary. The Windows pipe path is untested in this release.

The relay comparison also decides which process keeps the link port, and it carries the headless settings (see "Headless agents") as a one-way digest of the Foundry URL, world, user, sandbox setting and the stored-agent passwords this process holds. A password or a URL's credentials are never sent. A gateway that runs a headless agent is never displaced by a caller without headless settings: a caller with matching session settings (`publicUrl`, `serverMode`, `allowOrigins`) relays to it, otherwise it goes to standby. A primary from before headless support leaves a headless caller in standby until it exits. [headless.md](guides/headless.md#several-gateways-on-one-link-port) has the full rules and the exact messages.

### Multi-user isolation

- An MCP session is bound to one (world, user) pair, and its calls are routed to that pair's connection only. What happens when that pair goes away depends on how the gateway was started. With `--user <name>` (a Foundry user name or id) the binding is fixed: when that user is offline the call fails as offline, and the session never moves to another user (`gateway/test/routing/isolation.test.ts`). Without `--user`, which is the default for the `.mcpb` and for the commands in the guides, the gateway is in follow mode (`gateway/src/routing/binding.ts:187-215`, `gateway/test/routing/follow.test.ts`). A session still stays on its pair while that pair is connected. Once the bound pairing has no open connection and exactly one other active pairing is connected, the same session re-binds to that pairing, which can be a different user or world. It does so at once if that pairing connects after the bound one has gone, or at the next call once the bound pairing has been away 30 seconds (`REBIND_GRACE_MS`, `binding.ts:38`). With several other pairings connected it does not re-bind and reports the ambiguity. To keep a conversation from reaching a world or user that you pair later, start the gateway with `--user <name>`, or end the conversation.
- Module calls run as the real `game.user` that Foundry set for the connection, never as a user named in the call. Foundry's server attaches the sender's user id to every module socket message from the logged-in session, and a modified client could not change it in the experiments in `docs/spikes/foundry-socket-identity.md`. The payload of a message is attacker-controlled, so identity is never read from it. What Foundry cannot prove is who is at the keyboard, only which logged-in session sent the message.
- A pending call settles only from the socket it was sent to. A result or error frame from another connection carrying the same call id is ignored, and a replaced old socket cannot settle a call on the new one.
- **Server mode and remote access.** Only the operator decides who pairs as whom. The gateway cannot verify the world and user ids a module claims, and Foundry cannot prove to the gateway who is at the keyboard (`docs/spikes/foundry-socket-identity.md`). So each person pairs with an invite the operator mints for an exact (world, user), and the invite is the trust root: send it privately, because whoever holds it can pair as that user until it is used or expires. Pairing again as the same user needs a new invite, and redeeming it revokes the old pairing and that user's OAuth grants and tokens. The operator removes someone with `--revoke-pairing <world> <user>`, which also revokes their grants and cancels their unused invites; a running gateway closes their connection within about 5 seconds. An OAuth session is bound to the (world, user) of the grant that created it, never to one named in a request, and the code that proves control of that user's session is shown in their own Foundry window. Headless identities are never chosen by follow mode: they are reached only by explicit binding (`--world` with `--user <agent id>`). Over stdio or HTTP with the static bearer, a local-mode gateway reached the agent. A server-mode gateway with a public URL (as the Compose stack sets it) runs the agent. With a public URL, a remote OAuth client (a scripted one, not the claude.ai, ChatGPT or Gemini connectors) reached it through its owner's approval; the other client kinds run against a public URL did not. Without a public URL, an HTTP client with the static bearer reached it, from source and in the Docker image. A remote OAuth client reaches a headless agent only through its owner (see the owner bullet below). The table in [headless.md](guides/headless.md#3-reach-the-agent-from-your-ai-client) lists each combination that was run and the one that was not.
- **Local mode's trust assumption.** On first pairing the gateway trusts the world and user ids in the module's `hello` message, and it has no way to check them. Anyone who can reach the link port with a valid pairing code can therefore claim any user id. Local mode assumes that only the owner's machine can reach the link, and the gateway listens on loopback, checks the `Host` header and requires the one-time code for that reason. If you expose that port to other machines or let others use the machine, this assumption no longer holds.

### What a malicious agent can and cannot do

A compromised or misled agent can do anything its user's role, the world policy and the approvals allow, and nothing else. Code execution always needs a human approval. Destructive changes need approval by default, unless a GM's world policy allows them. It cannot run a tool its role does not list, cannot exceed the rate limits, cannot act as another user, and cannot hide an ordinary write from the audit journal. A GM can undo declared targets of the supported document types listed under Audit and Undo, but approved code can make changes that Undo cannot reverse, and can also erase or bypass the audit record, so approving code means trusting it with both. It can still waste approvals, read everything its user can read, and write what you approve. Be careful about approving anything you have not read, because the diff is the safeguard. Text in tool results, journal pages and pack descriptions is untrusted, and can try to steer the agent towards other tools you have connected to it.

A remote client adds a vendor between the agent and your world. The model runs in the vendor's cloud and everything it reads leaves your machine (see the privacy statement). Grant the narrowest scopes, `read` first. A remote client cannot exceed its token's scopes, cannot change the Foundry user its grant is bound to, and cannot reach another world or user; but a prompt injection in something it read can still spend its scopes, including asking for approvals. Approve with the same care as for a local agent. Revoking the grant ends its access at once.

### Tool packs

A tool pack is a separate Foundry module, so it is unsandboxed JavaScript in the GM's or player's browser with the same access as any other module. The core cannot stop a pack from reading what its user can read or calling Foundry directly.

What the core does guarantee is that every call to a pack tool goes through the same dispatcher pipeline as a core tool: argument validation, role, agent control, world policy, rate limit, approval and audit. A pack cannot shadow a core tool, register a tool without a category, or reach a handler that skips the pipeline. Pack tools carry a "Third-party tool pack" tag in approvals. Pack tool descriptions and results are untrusted text. To remove a pack, a GM disables the module and reloads the world, which also removes its tools.

## Public mode behind a reverse proxy — task 74

Run with `--public-url https://your.host` (or `AGENT_GATEWAY_PUBLIC_URL`) when the gateway is reachable from the internet. The gateway does no TLS: put it behind a reverse proxy such as Caddy that terminates TLS, keep the gateway bound to loopback, and pass `--trust-proxy` so per-client limits see the real client address. An `http:` public URL on loopback is accepted for testing and logs a warning. In this mode the static HTTP bearer is off, so remote clients authenticate only through OAuth (task 35). Pairing codes are printed only in the operator's log and console; they are never in `gateway_status`, not-connected errors or MCP log notices, so protect that log. `/status` shows only the version and uptime. Host and Origin are checked against the public URL. Failed codes and pending pairings are limited per client, so one source cannot lock out the rest, but a distributed flood can still block new pairings (paired clients are unaffected). A session with no fixed (world, user) is refused rather than falling back to follow mode. Back up the store with `--backup <path>` while the gateway runs; restoring means stopping it and replacing the database file.

## Remote access and OAuth

With `--public-url`, remote clients (claude.ai, ChatGPT, Gemini) connect to `/mcp` over HTTPS and authenticate with OAuth 2.1; there is no other way in. The design is in `docs/architecture.md`; here is what it protects against.

- **PKCE.** Authorization uses the authorization-code flow with S256 PKCE required. A request without a valid S256 `code_challenge` is refused, so a stolen code is useless without the verifier.
- **Exact redirect URIs.** A client registers its redirect URIs, at most 5, each `https` (or `http` on `127.0.0.1`, `[::1]` or `localhost`), with no fragment or credentials. At `/authorize` the redirect URI must equal a registered one exactly. Until it is known to match, the gateway shows an error page and redirects nowhere.
- **Audience binding.** Tokens are issued for the audience `<public URL>/mcp`. A request naming a different `resource` gets `invalid_target`, so a token cannot be replayed at another server.
- **Lifetimes.** Authorization codes last 60 seconds. Access tokens last 1 hour. Refresh tokens last 30 days and rotate on every use; reusing a rotated refresh token or a used code revokes the whole token family. The gateway stores only hashes of codes and tokens.
- **Consent is tied to the user's own session.** The consent page lets a person name the world and the Foundry user and pick scopes, but the one-time code that completes it is sent over the link to that user's Foundry window and shown there. Identity is never taken from the page. A client cannot reach a user whose window it cannot see.
- **Revocation from Foundry.** Each Foundry user lists and revokes their own grants under "Connected apps" in the module. Revoking, or revoking the pairing, ends the grant: the next call gets 401 and the client must ask again. The operator's `--revoke-pairing` revokes a user's grants too.
- **CSRF and framing on the consent page.** The consent form carries a per-request CSRF token that must match a `__Host-` cookie (Secure, HttpOnly, `SameSite=Strict`, 15 minutes), and the page refuses to be framed (`X-Frame-Options: DENY`) with a Content-Security-Policy (`default-src 'none'`, same-origin stylesheet only, `frame-ancestors 'none'`) that allows no script and no inline style.
- **Per-client limits.** Registration, `/authorize` and `/token` are rate limited per client address. Behind a proxy that address comes from `X-Forwarded-For`, trusted only with `--trust-proxy` from a loopback peer. See [reverse-proxy.md](guides/reverse-proxy.md). A distributed flood can still exhaust the limits for new sign-ins, though clients that are already signed in are unaffected. Client names are untrusted text, trimmed to printable characters and 100 characters, and shown escaped.
- **Scopes.** `read` is the default; `write`, `destructive` and `code` must be granted on the consent page. They filter the tool list and the call. They do not replace approvals.

Per-client setup is in the guides for [claude.ai](guides/claude-ai.md), [ChatGPT](guides/chatgpt.md), [Gemini CLI](guides/gemini-cli.md) and [the Gemini app](guides/gemini-app.md). Their manual checks are in [docs/compatibility.md](compatibility.md); none of them has been run. The automated conformance run tests the gateway's OAuth server with its own client and the MCP Inspector, not with claude.ai, ChatGPT or Gemini.

## Headless agents

A headless agent is a Foundry user the gateway logs in itself with its own Chromium ([guide](guides/headless.md)). What matters for security:

- **The agent user is not for humans.** Its pairings come only from invites the gateway mints for it. `headless add` revokes any pairing and OAuth grant that user already had, and cancels its unused invites, so a browser that was already using it must pair again.
- **The password is required, and kept out of the database.** The gateway refuses an empty one, because a Foundry user with no password can be logged into by anyone who reaches `/join`. The password lives only in the environment or in the 0600 config file, never in SQLite. There is no password flag, so it does not appear in a process listing. The `headless_agents` table stores no password, and the relay comparison between gateways carries only a one-way digest.
- **Chromium's sandbox.** It is on by default for npm and from-source installs, and off in the Docker image (`AGENT_GATEWAY_HEADLESS_NO_SANDBOX=1`), where it usually cannot start as a non-root user. Turning it off means a flaw in a page Chromium loads is not contained by Chromium's own sandbox, and falls back on the container or user account around it. Use a Foundry URL with a certificate that Node and Chromium both trust.
- **The profile directory.** Each (world, user) has a Chromium profile under `<state dir>/headless/profiles/`, mode 0700. It holds a logged-in Foundry session and the module's pairing token. Anyone who can read it can act as the agent user. `headless remove` keeps it, so delete it by hand when you are done.
- **The owner is a routing hint.** `--owner` sends the agent's ask-owner approvals, and the consent codes of remote OAuth clients asking for the agent's identity, to that Foundry user. It does not grant the owner or the agent any permission: the owner can approve a grant for the agent but cannot act as the agent or pair as it.
- **Two world switches guard it.** The module refuses every call from a headless agent while "Enable headless agents" is off, and, for an agent that is not a GM, while "Enable player agents" is off. Both are off until a GM ticks them in the "Configure policies" window and presses "Save policies". The agent is otherwise subject to its user's role, the world policy, approvals and the audit journal like any other agent.
- **Binding.** Follow mode never binds a session to a headless identity; reach one with `--world` and `--user <agent id>`. A local-mode gateway reached the agent over stdio or HTTP with the static bearer, and server mode without a public URL did over HTTP with the bearer. With a public URL (as the Compose stack sets it), the other client kinds run did not reach it; a remote OAuth client (scripted in the run) did, only through the agent's owner, as described in the next bullet.
- **Remote OAuth for a headless agent.** Only a stored agent added with `headless add --owner <id>` can be reached; the flag/env agent has no owner and cannot. The consent code goes to the owner's Foundry window, never to the agent's, and the owner must be connected to Foundry to receive it. The consent page looks the same for every target, so it never shows whether a name is a headless agent, has an owner, or whether the owner is online; if no code arrives the page gives no hint why. The grant is bound to the agent's pairing, not to the owner, and ends when the agent re-pairs (`headless add`, `headless remove`, redeeming a new invite for that user), after which the owner approves again. A gateway restart does not end it: the runner reconnects with its stored token.
