# Security boundaries

## Offline event reading — source verified, bounded GM native acceptance passed

Offline reading is an opt-in world setting, off by default. Task29 stores `{enabled:false, retentionDays:14}` and bounds retention to integer days from 1 to 365. PR #76 is merged. Source `e28f836ae8a83116d59f0f75174d684c9917c5a7` passed build/lint and 3,427 fast / 2,227 slow tests. Bounded GM native acceptance passed on Foundry 13.351/14.369; this does not broaden the software trust boundary.

Player gateways enforce this setting **by software, not cryptography**. The gateway trusts policy observations from its authenticated paired module; it does not independently attest that the sender is a native GM or that the world setting is still current. The legitimate module reads the world setting and restricts editing/purge controls to a freshly checked native GM. A modified gateway or paired client can evade these cooperative checks. An unreachable gateway cannot discover a later world-policy change; it uses the last accepted setting until an authenticated update arrives. This does not solve Task18's immediate cross-owner/offline invalidation blocker.

Offline reads require both a persisted enabled world policy and the exact active pairing's last accepted explicit read allow. Missing state, ask/deny/disabled authorization and revoked pairings fail closed. A fresh connection must clear or withhold prior read permission until that connection accepts valid affirmative metadata; a connection that drops before announcing cannot resurrect old offline permission. Sessions remain fixed to world/user/agent identity. First offline selection uses an unambiguous persisted exact ID, never a user-name fallback, and replacement pairings inherit neither prior authorization nor rows.

Retention uses gateway receipt time rather than event-supplied timestamps, running at startup and hourly. Purge and retention remove payloads transactionally while preserving monotonic cursor high-water and truthful deletion gaps. The purge target is the authenticated connection's world at that receiving gateway, not caller-supplied world/user IDs or every gateway in the network. The module's legitimate purge action requires fresh GM checks; the gateway's paired-module trust must not be presented as independent GM attestation. A correlated reply reports the deletion count without deleting credentials, policy or cursor high-water.

Both peers must upgrade together to protocol **5.0.0** for Task29's strict policy/purge frames. Earlier protocol4 native proof establishes only Task28's bounded online behavior. Task29 native acceptance at `88b27ca` / bundle `d19791ab` used actual GM policy saves, enabled/disabled offline reads and isolated-buffer purge/count checks, with original world setting and baselines restored. It does not establish native player/offline revocation, retention timing or installed deployment. Combined verification passed (build/lint, 3,437 fast / 2,227 slow); reusable-harness validation is merged in PR #78. Future native mutations still require scoped consent, isolated test-buffer storage and guarded restoration of any changed world setting.

## Offline write queue — source verified, native acceptance pending

Task30 queues intent for a known module-owned non-read tool using the exact active `(worldId, userId, agentId)` pairing and original MCP session. A previously accepted validated tool catalog permits bounded offline admission; it is not write authorization or proof that the native policy is still current. Unknown tools, reads, rejected catalogs and replacement pairings cannot inherit executable intent. Ordinary offline module reads remain `WORLD_OFFLINE`; Task29-authorized event reads and owner-scoped queued `approval_status` are explicit exceptions.

The reviewed contract bounds nonterminal intent to 20 entries per pairing and 500 globally, with a seven-day deadline from gateway receipt. Calls and delivery frames obey the protocol byte limit, and batches contain at most five entries. SQLite keeps at most 1,000 total receipts, retaining terminal outcomes for seven days; startup recovery and a single 60-second cleanup timer maintain expiry. Full storage refuses new work instead of silently evicting pending intent. An accepted `pending_approval` receipt means no human approval or execution has occurred. The receipt survives MCP session close; there is no public cancellation operation after acceptance.

Reconnect delivery requires the same authenticated active pairing and a fresh valid matching tool definition. The native dispatcher rechecks the current Foundry user, role, tool arguments, availability, effective category and policy, including prepared macro/script source. Policy denial and disabled agents remain denied; stricter GM approval remains stricter. Otherwise replay requires fresh explicit once approval. Earlier session grants cannot approve replay or be created from it. Immutable queue identity, arguments, prepared source, deadline, native permissions and current replay connection must still hold immediately before execution.

A dedicated browser localStorage receipt guards replay before dispatch, with synchronous write verification, at most 1,000 receipts, a five-million-character encoded bound and seven-day retention. The gateway claims intent before delivery. Duplicate and reordered frames cannot authorize another owner or run a claimed handler again. Undelivered intent past its deadline becomes `expired`; already claimed or pending work with an uncertain outcome after disconnect, restart or deadline becomes `unknown`, requiring reconciliation rather than automatic resend. This does not promise exactly-once world effects across browser or gateway crashes, automatic rollback or cancellation. Browser receipt persistence is cooperative local storage, not a tamper-proof distributed execution log.

Both peers must upgrade together to protocol **6.0.0**. This retains the paired-module software trust boundary described above and does not resolve Task18's unreachable-revocation problem. Source `b320505daaec9928fc5908cf938874948c5be240` passed build/lint and the required full gate (3,487 fast / 2,227 slow tests). Both independent reviews passed; the independent 213-test selection passed separately. Task29's native results do not establish Task30 replay, approval or crash behavior. Fresh scoped consent is required before native Task30 writes; no production queue mutation or deployment is claimed.
