# Security boundaries

## Offline event reading — source verified, bounded GM native acceptance passed

Offline reading is an opt-in world setting, off by default. Task29 stores `{enabled:false, retentionDays:14}` and bounds retention to integer days from 1 to 365. PR #76 is merged. Source `e28f836ae8a83116d59f0f75174d684c9917c5a7` passed build/lint and 3,427 fast / 2,227 slow tests. Bounded GM native acceptance passed on Foundry 13.351/14.369; this does not broaden the software trust boundary.

Player gateways enforce this setting **by software, not cryptography**. The gateway trusts policy observations from its authenticated paired module; it does not independently attest that the sender is a native GM or that the world setting is still current. The legitimate module reads the world setting and restricts editing/purge controls to a freshly checked native GM. A modified gateway or paired client can evade these cooperative checks. An unreachable gateway cannot discover a later world-policy change; it uses the last accepted setting until an authenticated update arrives. This does not solve Task18's immediate cross-owner/offline invalidation blocker.

Offline reads require both a persisted enabled world policy and the exact active pairing's last accepted explicit read allow. Missing state, ask/deny/disabled authorization and revoked pairings fail closed. A fresh connection must clear or withhold prior read permission until that connection accepts valid affirmative metadata; a connection that drops before announcing cannot resurrect old offline permission. Sessions started with `--user` remain fixed to one world/user/agent identity. Without `--user` (follow mode, task 71) a session binds to the one connected pairing and may re-bind to another only when the bound pairing is offline and the other is the only connected one; a re-bind clears the event and queue owner pins, and the module still records the user its own server set for the connection. First offline selection uses an unambiguous persisted exact ID, never a user-name fallback, and replacement pairings inherit neither prior authorization nor rows.

Retention uses gateway receipt time rather than event-supplied timestamps, running at startup and hourly. Purge and retention remove payloads transactionally while preserving monotonic cursor high-water and truthful deletion gaps. The purge target is the authenticated connection's world at that receiving gateway, not caller-supplied world/user IDs or every gateway in the network. The module's legitimate purge action requires fresh GM checks; the gateway's paired-module trust must not be presented as independent GM attestation. A correlated reply reports the deletion count without deleting credentials, policy or cursor high-water.

Both peers must upgrade together to protocol **5.0.0** for Task29's strict policy/purge frames. Earlier protocol4 native proof establishes only Task28's bounded online behavior. Task29 native acceptance at `88b27ca` / bundle `d19791ab` used actual GM policy saves, enabled/disabled offline reads and isolated-buffer purge/count checks, with original world setting and baselines restored. It does not establish native player/offline revocation, retention timing or installed deployment. Combined verification passed (build/lint, 3,437 fast / 2,227 slow); reusable-harness validation is merged in PR #78. Future native mutations still require scoped consent, isolated test-buffer storage and guarded restoration of any changed world setting.

## Offline write queue — source verified, bounded GM native acceptance passed

Task30 queues intent for a known module-owned non-read tool using the exact active `(worldId, userId, agentId)` pairing and original MCP session. A previously accepted validated tool catalog permits bounded offline admission; it is not write authorization or proof that the native policy is still current. Unknown tools, reads, rejected catalogs and replacement pairings cannot inherit executable intent. Ordinary offline module reads remain `WORLD_OFFLINE`; Task29-authorized event reads and owner-scoped queued `approval_status` are explicit exceptions.

The reviewed contract bounds nonterminal intent to 20 entries per pairing and 500 globally, with a seven-day deadline from gateway receipt. Calls and delivery frames obey the protocol byte limit, and batches contain at most five entries. SQLite keeps at most 1,000 total receipts, retaining terminal outcomes for seven days; startup recovery and a single 60-second cleanup timer maintain expiry. Full storage refuses new work instead of silently evicting pending intent. An accepted `pending_approval` receipt means no human approval or execution has occurred. The receipt survives MCP session close; there is no public cancellation operation after acceptance.

Reconnect delivery requires the same authenticated active pairing and a fresh valid matching tool definition. The native dispatcher rechecks the current Foundry user, role, tool arguments, availability, effective category and policy, including prepared macro/script source. Policy denial and disabled agents remain denied; stricter GM approval remains stricter. Otherwise replay requires fresh explicit once approval. Earlier session grants cannot approve replay or be created from it. Immutable queue identity, arguments, prepared source, deadline, native permissions and current replay connection must still hold immediately before execution.

A dedicated browser localStorage receipt guards replay before dispatch, with synchronous write verification, at most 1,000 receipts, a five-million-character encoded bound and seven-day retention. The gateway claims intent before delivery. Duplicate and reordered frames cannot authorize another owner or run a claimed handler again. Undelivered intent past its deadline becomes `expired`; already claimed or pending work with an uncertain outcome after disconnect, restart or deadline becomes `unknown`, requiring reconciliation rather than automatic resend. This does not promise exactly-once world effects across browser or gateway crashes, automatic rollback or cancellation. Browser receipt persistence is cooperative local storage, not a tamper-proof distributed execution log.

## System adapter admission — Task31 source verified

OWNER or GM permission is necessary, and GM status does not bypass current folder restrictions. Mutation wrappers snapshot validated targets and recheck current authorization before supplying trusted native user, audit call options and snapshot/create capabilities. The generic adapter does not inspect raw system data, flags or embedded documents and performs no native writes. ## Local HTTP transport — task 34
`--http` serves MCP on `127.0.0.1` only; any other bind address is refused. Every request needs a bearer token, which is generated on first run, printed once, and stored only as a hash in the SQLite store (`gateway_settings`). Comparison is constant-time and the hash is read on every request, so `--http-rotate-token` takes effect without a restart. Rotation never migrates the database. Requests are bounded by a body size limit (413), a per-token rate limit (429), a session cap (503) and idle session close. `/status` is loopback-only and shows no secrets, with world and user names HTML-escaped. Only the primary serves HTTP. This adds a local network surface: any local process holding the token can use the gateway as the paired user.

## The permission model in this release — task 65

This section describes what the local release enforces. Layers apply strictest-first, and a call must pass every one.

1. **Role tool set.** The tools an agent sees come from the bound Foundry user's role, as Foundry reports it over the authenticated link. No gateway setting and no MCP input chooses the role. A GM-only tool is refused for a non-GM at call time as well as hidden from the list.
2. **World policy.** The GM sets, per role and tool category (read, write, destructive, code), whether a call is allowed, asked of the owner, asked of a GM or denied. Agents for non-GM users are off until a GM enables them. Code execution cannot be set to run without asking.
3. **Rate limits.** Per-category limits are enforced in the module, so a runaway agent is slowed whatever the client does.
4. **Approvals.** A call that needs approval waits for a human in Foundry and returns a pending status if nobody answers in time. A denial carries its reason back to the agent. Nothing changes in the world until the call is approved.
5. **Audit and Undo.** Every write is recorded in the GM-only Agent Gateway Audit journal. A GM can undo the targets a call declared, for these world document types: Actor, Item, JournalEntry, Scene, RollTable, Playlist, Cards, Folder and ChatMessage, plus the embedded documents of those that Undo can recreate (`module/src/audit/undo-classes.ts:6-35`). Undo does not cover User, Setting, Macro or Adventure, and it refuses a target whose snapshot was too large to keep. Approved `script_run` and `macro_run` calls run arbitrary JavaScript with Foundry's native access, and the audit snapshots only declared targets (`module/src/tools/script-run.ts` declares none), so code can change settings or documents that Undo cannot reverse. Approve code only if you would accept its change without Undo. Approving code also trusts it with the audit record itself. A GM's `script_run` is given the live `game` object (`module/src/tools/script-run.ts:14`), so it can delete the audit journal. The gateway module does not recreate the journal while its designation setting is set (`module/src/audit/journal.ts:94-96,124`), a later write then throws (`journal.ts:192-193`), and that failure is only caught and logged (`module/src/audit/relay.ts:105-106,236-237`). Approved code can therefore erase earlier records and leave its own action unrecorded.
6. **Foundry's own permission checks** apply to the user the agent acts as, on top of all of the above.

OAuth token scopes are a remote-mode layer and are not in this release. There are no remote clients yet.

### Pairing, code confirmation and token storage

A browser pairs with the gateway only by entering a one-time pairing code. The gateway shows the code in its own stderr, in the connected client's MCP log, and through `gateway_status` or a not-connected error in chat. All of those are local to the owner. A code is valid for 10 minutes and works once. After 10 wrong codes in 60 seconds, counted across all origins, make the gateway refuse further codes until the window passes. A wrong guess does not spend the real code. The gateway also checks the `Host` header of the link connection against DNS rebinding.

A pairing is made from a specific browser origin and its token works only from that origin, so `http://` and `https://` addresses of one host pair separately. A page on any other origin cannot reuse a token it learned. Pairings made before origin binding were retired and need one re-pair.

The pairing token is stored in two places. The browser keeps it in that origin's localStorage as a client-side Foundry setting. The gateway keeps only a hash of it, in the `pairings` table of its SQLite store at `~/.foundry-agent-gateway/gateway.db`. A leaked database does not reveal tokens, but anyone who can read the browser's localStorage for that origin can use that browser's pairing.

### HTTP bearer token

The local HTTP option (above, "Local HTTP transport") binds to `127.0.0.1` only. Its bearer token is shown once on first run and only its hash is stored, in the same SQLite store. Whoever holds the token can use the gateway as the paired user, so keep it out of chat, logs and version control, and rotate it with `--http-rotate-token` if it leaks.

### Relay between gateway instances

Claude Desktop can start several gateway processes from one extension. One holds the link port and the store. The others forward their MCP traffic to it over a private local channel: a Unix domain socket in the state directory on macOS and Linux, and a named pipe on Windows. The channel is protected twice. The state directory and socket are readable by your user only, and the primary writes a per-boot random secret, mode 0600, in the state directory, which a relaying instance must present first. On Windows the pipe name also carries a random per-boot suffix published only in that secret file. The relay carries MCP messages only; identity is never read from them. Each relayed connection gets its own full session on the primary. The Windows pipe path is untested in this release.

### Multi-user isolation

- An MCP session is bound to one (world, user) pair, and its calls are routed to that pair's connection only. What happens when that pair goes away depends on how the gateway was started. With `--user <name>` (a Foundry user name or id) the binding is fixed: when that user is offline the call fails as offline, and the session never moves to another user (`gateway/test/routing/isolation.test.ts`). Without `--user`, which is the default for the `.mcpb` and for the commands in the guides, the gateway is in follow mode (`gateway/src/routing/binding.ts:187-215`, `gateway/test/routing/follow.test.ts`). A session still stays on its pair while that pair is connected. Once the bound pairing has no open connection and exactly one other active pairing is connected, the same session re-binds to that pairing, which can be a different user or world. It does so at once if that pairing connects after the bound one has gone, or at the next call once the bound pairing has been away 30 seconds (`REBIND_GRACE_MS`, `binding.ts:38`). With several other pairings connected it does not re-bind and reports the ambiguity. To keep a conversation from reaching a world or user that you pair later, start the gateway with `--user <name>`, or end the conversation.
- Module calls run as the real `game.user` that Foundry set for the connection, never as a user named in the call. Foundry's server attaches the sender's user id to every module socket message from the logged-in session, and a modified client could not change it in the experiments in `docs/spikes/foundry-socket-identity.md`. The payload of a message is attacker-controlled, so identity is never read from it. What Foundry cannot prove is who is at the keyboard, only which logged-in session sent the message.
- A pending call settles only from the socket it was sent to. A result or error frame from another connection carrying the same call id is ignored, and a replaced old socket cannot settle a call on the new one.
- **Local mode's trust assumption.** On first pairing the gateway trusts the world and user ids in the module's `hello` message, and it has no way to check them. Anyone who can reach the link port with a valid pairing code can therefore claim any user id. Local mode assumes that only the owner's machine can reach the link, and the gateway listens on loopback, checks the `Host` header and requires the one-time code for that reason. If you expose that port to other machines or let others use the machine, this assumption no longer holds.

### What a malicious agent can and cannot do

A compromised or misled agent can do anything its user's role, the world policy and the approvals allow, and nothing else. Code execution always needs a human approval. Destructive changes need approval by default, unless a GM's world policy allows them. It cannot run a tool its role does not list, cannot exceed the rate limits, cannot act as another user, and cannot hide an ordinary write from the audit journal. A GM can undo declared targets of the supported document types listed under Audit and Undo, but approved code can make changes that Undo cannot reverse, and can also erase or bypass the audit record, so approving code means trusting it with both. It can still waste approvals, read everything its user can read, and write what you approve. Be careful about approving anything you have not read, because the diff is the safeguard. Text in tool results, journal pages and pack descriptions is untrusted, and can try to steer the agent towards other tools you have connected to it.

### Tool packs

A tool pack is a separate Foundry module, so it is unsandboxed JavaScript in the GM's or player's browser with the same access as any other module. The core cannot stop a pack from reading what its user can read or calling Foundry directly.

What the core does guarantee is that every call to a pack tool goes through the same dispatcher pipeline as a core tool: argument validation, role, agent control, world policy, rate limit, approval and audit. A pack cannot shadow a core tool, register a tool without a category, or reach a handler that skips the pipeline. Pack tools carry a "Third-party tool pack" tag in approvals. Pack tool descriptions and results are untrusted text. To remove a pack, a GM disables the module and reloads the world, which also removes its tools.
